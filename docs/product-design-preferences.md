# Block 产品设计偏好与判断准则

整理日期：2026-11-17。来源：M3 期间的设计要求、纠正、实际界面评审，以及用户要求沉淀的深入分析。

这份文档帮助后续设计理解决定背后的取舍。各节区分已经明确的要求、从案例形成的归纳，以及后续评审可以使用的问题。归纳仍需接受新案例检验；用户的新决定优先，具体尺寸、颜色、样式和时长不自动成为永久规范。

本文件不授予实施、提交或发布权限，也不替代验收台账。当前产品决策见[任务与产品方向](next-tasks.md)，页面验收见[逐场景记录](scene-review-status.md)及[交接中的用户页面验收](../UI_REFINEMENT_HANDOFF.md#用户页面验收)。历史记录按其日期和范围理解。

## 核心理解

M3 中反复出现的判断是：界面应当清楚表达对象、状态和操作之间的关系，让用户自然地完成事情。紧凑、克制、一致和连贯，是实现这一目标的手段。

设计评审先回答三个问题：

1. 这段信息属于谁？
2. 这个动作把用户带到哪里？
3. 用户能否理解并掌握它的结果？

确定这些关系后，再决定控件、间距、颜色和动画。

## 1. 简化理解路径，减少特殊分支

**明确案例。** 用户先前要求单游戏数量入口不可点击，随后修正为：“改成允许点击查看，但不允许勾选去除（强制勾选），这样才能选择隔离方式。” 又明确要求第一层来源 Drawer 不展示单游戏的具体隔离策略。当前路径是来源 → 实例列表 → 共享/隔离策略；单游戏同样沿用这条路径，但唯一实例保持选中。

**归纳。** 简化可以通过减少用户需要学习的分支实现。即使保留一次导航，只要单个和多个对象沿用相同流程，用户就更容易预测操作结果。点击次数只是评价效率的一部分。

**后续判断。** 为特殊数量或状态增加快捷入口前，检查它是否改变页面职责、隐藏必要设置，或让用户需要重新学习操作路径。方便与一致发生冲突时，说明具体收益和代价再作选择。

## 2. 用布局表达信息归属

**明确案例。** 用户要求将可点击的游戏数量放在来源卡片标题旁，纠正了把它放到 Drawer 标题或其他选择器中的误解。按钮与标题虽然已经同行，用户仍指出两者距离过远。策略页则要求实例名稍小并加粗，在同行另一侧展示版本与 Loader。

**归纳。** 位置、距离和字重共同表达信息属于哪个对象。来源标题与数量应当被读成一个组合；实例名与版本信息应当容易对应，又具有主次。

**后续判断。** 检查实际文字和操作之间的距离，而不只检查容器同行、对齐或互不重叠。确认用户能从视觉关系直接读出业务关系。

## 3. 让信息本身成为清楚的操作入口

**明确案例。** 用户喜欢将数据模式文字作为入口，并提出虚线下划线，以及让游戏数量入口采用同一设计。数量应反映当前选中的实例数。卡片选择、查看实例和编辑策略仍各有明确动作。

**归纳。** 当用户看到的内容就是要处理的对象时，直接操作这段内容可以减少重复说明和泛化按钮。虚线与箭头负责提示可操作性；入口的文字负责说明对象或当前状态。

**后续判断。** 减少控件后，仍要能辨认哪里可点、点击会发生什么，以及它是否影响选择。避免为了扩大点击区域，让查看详情与改变勾选意外耦合。

## 4. 优先统一行为和语义，再统一形式

**明确案例。** 用户要求单选项统一使用 Radio、同类数量入口统一样式，并让 Drawer 内各层页面使用一致的平移。另一方面，用户撤回了“没有返回按钮也保留占位”的要求，恢复无返回按钮时的标题布局。

**归纳。** 一致性存在不同层次。相同动作的反馈、相同层级的导航、相同控件的含义，应当稳定。形式上的对齐需要服务于实际内容和操作。

**后续判断。** 复用组件时保留页面职责。不要把不同动作合并成一个事件，也不要仅为模板整齐增加无用途的空位。出现差异时，先判断它是否来自真实的语义差异。

## 5. 用内容组织实现紧凑，同时保留留白

**明确案例。** 用户要求所有页面采用 Home 的 360 × 720 逻辑内容尺寸，允许为此重做布局与交互。同时要求统一卡片圆角、调整 Item 内衬与纵向间距，保留 Drawer 左右对称正文边距，把滚动条移入右侧留白。重复 Label、冗长说明和无助于识别的装饰应精简。

**归纳。** 小窗口依靠分层、主次和内容取舍维持可读性。较少的内容可以获得足够的空间；尺寸紧凑与舒适的留白可以同时成立。

**后续判断。** 空间不足时，先检查页面是否承担过多职责、信息是否重复、说明是否适合当前步骤，再考虑缩小字号或内衬。检查实际文字行高和可见边距，避免样式数值相同但视觉留白不同。

360 × 720 是当前明确的产品尺寸约定。局部间距、字号和入口形式随场景评审调整，不能仅凭一次调整推广到所有组件。

## 6. 让动效表达变化与页面关系

**明确案例。** 用户要求检查对勾的绘制过程、Radio 的变化、风险说明出现时的卡片扩张，以及实例列表进入隔离策略时与来源进入列表一致的平移。

**归纳。** 动效帮助用户感知哪个对象发生变化、哪里展开了内容、进入了哪一层以及返回到哪里。完成一次操作，包含结果出现和中间过程连贯这两部分。

**后续判断。** 为动效明确它所表达的变化。检查进入、退出、返回及中断时是否连贯，同类路径是否一致。结合已有减少动态效果要求保留即时、可用的结果；具体曲线和时长属于实现与原生调校，不视为用户永久指定的参数。

## 7. 自动处理机械事务，让重要后果可理解、可选择

**明确案例。** 用户要求自动确定游戏库路径并移除多余的 Change 入口；共享/隔离关系到存档、配置和维护，则通过适当位置的 Alert 引导到当前 Drawer 内的策略页。明确隔离只需简短状态说明，不能确定时默认隔离并解释风险。用户允许清理旧 Block 数据结构及 API，同时要求尊重已有 `.minecraft` 结构。

**归纳。** 产品可以承担重复、机械的整理工作，而重要的数据后果需要保持可见并可由用户决定。内部概念的简化应降低用户负担，不能把改造成本转嫁到用户的游戏内容上。

**后续判断。** 对自动决定，说明依据与结果；对需要选择的事项，说明影响并提供就近入口。区分原数据被删除与当前隔离目录中看不到原数据。短暂操作反馈使用 Toast，持续影响选择的风险保留在相应页面。

## 设计评估与更新方式

用户明确要求研究优秀 UI 框架与桌面应用，逐页检查布局和交互，检查操作之间的衔接，并打磨微动效。研究应帮助理解机制和取舍，最终仍以 Block 的真实任务和原生界面为评审对象。

评审时沿完整操作路径观察：入口是否清楚，下一步是否自然，返回后是否仍能理解所在位置和已有选择。测试、截图与原生操作提供证据；用户确认决定验收范围。Welcome 的局部验收和 Import Games Drawer 的整体验收分别记录，不能互相扩展。

后续更新遵循以下方式：

- 新的明确决定替换冲突的旧决定，同时保留调整的原因和适用范围。
- 归纳遇到反例时重新分析，不用旧总结否定用户的新选择。
- 将单次参数调整留在对应组件或场景文档中；只有反复成立的判断才提升为一般准则。
- 不从这些偏好推导未表达的品牌风格、颜色倾向、全面去图标要求或“所有流程都要最少点击”等规则。

最常见的误读包括：把简洁等同于减少控件，把统一等同于固定占位，把小窗口等同于压缩间距，把少一次点击视为天然更优。设计提案需要说明它如何改善信息归属、操作路径和结果理解，而不仅是满足这些表面指标。
