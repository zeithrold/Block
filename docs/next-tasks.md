## v0 product intent and recovery policy (user decisions, 2026-10-23)

These decisions refine the assessment backlog below; they are product requirements, not claims of implemented or verified behavior. On 2026-10-23 the user authorized the custom-chrome increment and subsequently the shared Toast/Drawer component work. Their implementation and verification boundaries are recorded separately. Other product changes remain planning work unless separately requested.

- **Audience:** welcome players coming from PCL who do not understand Java and want to create a game with very few decisions, play with friends, and understand failures. Adopt this ease-of-use expectation rather than reproducing PCL's entire feature set.
- **Home:** retain the prototype's restrained Home with minimal design changes. Preserve its composition, visual character, primary action and lightweight selection entry points; limit adjustments to necessary state semantics, readability and demonstrated defects. Keep the primary play action and necessary context concise; place detailed configuration, installation diagnostics and management in their respective flows. Do not turn Home into a dashboard, add permanent status panels or substantially rearrange it to satisfy individual backlog findings.
- **Window chrome:** macOS traffic lights must be removed; integrating or repositioning them is not an acceptable substitute. This supersedes the earlier native-traffic-light requirement. Preserve a usable close/minimize/drag path within the restrained product chrome. The previous Windows/Linux system titlebars were an implementation choice, not a prohibition on custom chrome. The authorized implementation uses published GPUI APIs for client decorations and records actual platform/compositor constraints. Do not claim that fixed-size windows or native rendering require a system titlebar. The macOS removal and Windows/Linux custom-chrome increment are approved for implementation; visual acceptance remains with the user.
- **Daily use and page responsibilities:** in the ordinary Bundled experience, present one player-facing Game with its name, version and associated saves/mods/settings, rather than requiring users to understand Instance/Profile relationships. Keep Separated mode as an advanced capability and preserve the existing underlying catalog. Home is for playing and switching the current game/account; Games is for creation and management, Accounts for identity tasks, and Settings for launcher behavior and new-game defaults. Restore the last valid game/account selection on reopening, reuse valid sign-in, and do not repeat technical setup for an already configured game.
- **Launcher during gameplay:** default to minimizing Block after a successful game start and restoring it after the game exits. Provide a setting to keep the launcher window visible instead. Keep preparation, download and launch failures visible; define and verify a reliable success signal rather than treating process creation alone as proof that the game is usable. Restore the same game context and show failure help when appropriate. Closing Block must leave the independently supervised game running. Restoration applies while Block is still running; it must not relaunch a launcher the user closed.
- **First run (updated 2026-10-24):** Home-sized Welcome, optional source Drawer, then Account/Game task cards. Continue prefers account-first but either task may be completed first. Each Wizard saves independently. Existing adjacent `.minecraft` games and official-launcher installations are copied; the latter supports batch selection. Recommended setup pins a stable Vanilla release with automatic Java; Custom setup retains explicit choices. Finish returns Home and starts resource preparation. Completed work survives cancel/skip/restart. See [the approved implementation and validation plan](onboarding-implementation-plan.md); detailed account/game Wizard polish remains the following interaction pass.
- **Java:** detect existing installations and reuse a compatible one before downloading another. Compatibility includes the target game's requirements, OS and architecture; an incompatible installed Java does not satisfy detection. If no compatible runtime exists, download the most suitable compatible runtime from official sources. Most suitable does not mean newest. Keep manual selection in Custom installation and put technical version/path information in secondary detail.
- **Scope:** use global official sources. Do not add BMCLAPI, China-specific mirrors/acceleration or an end-to-end OptiFine download/install flow to v0. Existing user-supplied official OptiFine JAR support is not removed by this scope decision. Do not actively promote Offline mode in onboarding or Home.
- **Modpacks:** the eventual first import scenario is a local modpack file sent by a friend. Modpack capability is deferred beyond the current v0 scope, with no promised follow-up milestone; do not make it a v0 gate or present a nonfunctional third onboarding choice. Format coverage and service/download constraints require their own later assessment.
- **Failure help:** explain the observed problem in plain language, distinguish a known cause from a hypothesis, offer an actionable next step when supported, and provide one-click diagnostic export for difficult cases. Export should assemble useful game/loader/Java/system context and relevant logs without login credentials; users share the resulting file themselves.

The three recovery levels below describe product behavior, not P1/P2/P3 backlog priority. Classify by the proposed action and evidence, not merely by the error name. Use Level 1 only for verifiable, reproducible resources owned and managed by Block; changes to user choices require Level 2, and unsupported or uncertain remedies require Level 3.

| Level | Product behavior | Examples and boundaries |
| --- | --- | --- |
| 1 — Automatic recovery with Toast | Perform bounded recovery without confirmation and show a concise Toast stating what Block is doing. Update/coalesce feedback for the same task rather than stacking messages. Keep progress in the task page; if recovery fails, retain the error and next actions there. | Resume/retry the same interrupted download; reacquire a managed file with a trusted expected checksum after failed verification; fetch missing dependencies from the already selected official installation plan; repair an incomplete Block-managed runtime installation using the same selected compatible version. Do not overwrite unverified user changes, touch a running session, silently switch versions/sources, or retry indefinitely. Lack of sufficient ownership/integrity evidence excludes automatic replacement. |
| 2 — Explain and ask before changing state | Explain the proposed change, its target and likely effect, then offer an explicit action. Keep the current state if the user declines. | Adjust memory/JVM arguments; select a different Java for an existing game; change game/loader versions; disable/replace mods; reset configuration; move/delete player data or retained storage copies. An unsupported diagnosis is not sufficient to recommend any of these as a known fix. Never modify an external Java installation automatically. |
| 3 — Explain limits and support handoff | State what is known, what remains uncertain and any supported next step. Offer one-click diagnostic export for technical handoff. Do not apply speculative fixes. | Unknown crashes, uncertain mod conflicts, unsupported runtime/graphics environments, and ambiguous ownership/lock/session failures. Do not delete reservation markers, terminate processes or remove mods as a generic repair. A clear environment limitation may be explained confidently even when Block cannot repair it. |

Apply the levels to common remaining cases as follows:

| Case | Classification and next step |
| --- | --- |
| Interrupted network transfer or failed checksum of a managed download | Level 1 within bounded retries and trusted resource identity; after exhaustion, retain a clear failure with Retry/details rather than an endless Toast loop. |
| Missing or incomplete managed Java for the selected plan | Level 1 when the required version is known and the destination is owned by Block; choosing a different runtime for an existing game is Level 2. |
| Detected incompatible user-selected Java | Level 2: explain and offer selection of a compatible runtime without changing the external installation. Initial Quick start provisioning follows the automatic Java rule above. |
| Memory/JVM, mod, loader or game configuration changes | Level 2 only for an evidence-backed proposal; uncertain cause or no supported proposal is Level 3. |
| Expired sign-in or denied account access | Explain and provide a sign-in/retry action under Level 2; never silently switch identities or fall back to Offline mode. No technical export is necessary for a straightforward sign-in requirement. |
| Explicit disk-space or permission failure | Explain the affected location and offer a specific user-controlled action under Level 2. Do not silently delete files, change permissions or relocate data. Ambiguous causes use Level 3. |
| Existing active session, unexplained lock or stale reservation | Wait for a known active operation where applicable; no destructive automatic recovery. Explain a known recovery procedure under Level 2, otherwise use Level 3 and preserve evidence. |
| Unsupported graphics/runtime environment or unknown game crash | Level 3: explain proven limits, label hypotheses and offer diagnostic export. Do not promise an automatic driver/environment fix. |
