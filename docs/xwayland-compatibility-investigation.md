# KDE Xwayland chrome compatibility investigation

Date: 2026-10-23. Result: the earlier inert drag did not establish a GPUI defect. A correctly targeted drag delivered through the task-owned uinput device reached the public GPUI X11 move path and moved the KDE Xwayland window. Close, minimize/restore, content, and in-window overlay interactions also worked. The remaining boundary is strict fixed sizing: GPUI 0.3.9's X11 backend advertises the window as resizable to KWin even when the app requested `is_resizable: false`.

## Geometry and input provenance

This run's X11 client drawable was 640 × 420 at `(320, 168)`. KWin reported a 600 × 380 frame at `(340, 188)`: a 20 px inset on every side, also reported by `_GTK_FRAME_EXTENTS`. The initial screenshot shows the visible frame and rendered app content inside that inset. The WM and X11 rectangles must be sampled per run; another earlier receipt had a 680 × 460 drawable around a 640 × 420 frame, so those older dimensions do not describe this run. KWin's before/after snapshots and window screenshot are preserved in [the raw receipts](../target/chrome-probe/deepseek-xwayland/remote-receipts/).

The first drag automation used drawable coordinates as if the drawable origin were the visible frame origin. Its pointer landed in the 20 px CSD inset, produced no GPUI pointer callback, and did not move the window; this is an automation-coordinate miss. After measuring the current KWin frame and targeting its visible header, XTest reached the probe's pointer-down handler and GPUI logged `start_window_move_request`, but KWin geometry did not change in that XTest attempt. A task-owned virtual mouse created through `/dev/uinput` and using the same corrected header region produced the same GPUI move request and moved KWin's frame from `(340, 188)` to `(388, 220)` and X11 client from `(320, 168)` to `(368, 200)`, a `+48,+32` move. The log and exact per-step input calibration are in [drag-uinput-corrected.json](../target/chrome-probe/deepseek-xwayland/remote-receipts/drag-uinput-corrected.json); the earlier coordinate miss and XTest comparison are retained in [drag-xdotool.json](../target/chrome-probe/deepseek-xwayland/remote-receipts/drag-xdotool.json) and [drag-corrected-xdotool.json](../target/chrome-probe/deepseek-xwayland/remote-receipts/drag-corrected-xdotool.json).

This proves that the public GPUI drag path works under KDE Xwayland when driven through the tested user-like input device. It also records an observed difference between XTest and uinput for the WM move result. The evidence does not establish why KWin left the XTest move request inert; it does not justify attributing a defect to GPUI or asserting a KWin input-security rule. The initial failed attempt was both mis-targeted and an automation path that did not represent physical input.

The published X11 implementation's [`send_moveresize` and `start_window_move`](../target/chrome-probe/deepseek-xwayland/published-source/gpui-pre-linux-0.3.9/src/linux/x11/window.rs) path ungrabs the pointer, reads the root pointer position, then sends `_NET_WM_MOVERESIZE` with the move flag. The probe trace confirms that the GPUI request was made on the Xwayland run; the uinput result confirms KWin acted on it. These are direct observations against the locked published source, not a source-only capability claim.

## Fixed-size boundary and next step

The generic probe's maximize button and double-click zoom are absent in `--fixed-controls`. GPUI's [`Window::start_window_resize` and `is_resizable`](../target/chrome-probe/deepseek-xwayland/published-source/gpui-pre-0.3.9/src/window.rs) gate GPUI-initiated resize requests. However, the published Linux X11 backend does not use `WindowParams.is_resizable` when setting `WM_NORMAL_HINTS`; it advertises the GPU texture limit as the maximum size in [`x11/window.rs`](../target/chrome-probe/deepseek-xwayland/published-source/gpui-pre-linux-0.3.9/src/linux/x11/window.rs). KWin consequently reported the window as resizable. This run did not demonstrate that an end user can resize it through a particular KWin shortcut, but the public API does not prove a strict fixed-size policy on this backend. Production may proceed with titlebar removal, drag, minimize, close and in-window dialogs without a GPUI patch. Keep fixed-size enforcement as a separate integration requirement; do not claim it is guaranteed on KDE Xwayland until the user-facing WM paths are validated or a compatible size-constraint path is identified.

### Proposed To-Do delta (English; for Codex to reconcile)

Keep strict fixed-window enforcement pending a native user-path check or a compatible constraint mechanism.
